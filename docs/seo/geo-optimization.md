**更新日期**：2026-08-11
**目标引擎**：Google AI Overview、ChatGPT Search、Claude、Perplexity、Gemini、Bing Copilot

## 一、先说清楚 GEO 到底是什么

「GEO（Generative Engine Optimization）」这个词现在被大量滥用，很多说法本质是包装过的旧 SEO 话术。剥掉噱头后，AI 搜索的引用机制大致是：

1. **检索**：LLM 通过搜索后端（Google / Bing / 自建索引）拿到候选页面——**这一步依然是传统 SEO**。进不了检索结果，后面的都不存在。
2. **解析**：把 HTML 转成文本，提取结构。标题层级、列表、表格、结构化数据在这里起作用。
3. **摘录**：从页面中挑出能直接回答用户问题的片段。
4. **归因**：决定是否给出链接引用。

由此得出三条务实结论：

- **GEO 的地基是 SEO。** 本次修复的 canonical 问题，对 AI 搜索的影响和对 Google 搜索一样致命——页面进不了索引，就不会被任何 AI 检索到。
- **可摘录性 > 关键词密度。** LLM 需要的是「一段能直接回答问题的自足文字」，不是关键词覆盖率。
- **事实密度与可核实性决定引用意愿。** 含具体数字、年份、出处的段落更容易被引用；营销辞令会被跳过。

## 二、已实施的动作

### 2.1 答案前置区块（最重要的一条）

支柱长文、3 篇博客、英文首页均以 `.key-answer` 区块开头：

```html
<div class="key-answer">
  <p><strong>一句话回答：</strong>艾宾浩斯遗忘曲线是 1885 年由德国心理学家
  赫尔曼·艾宾浩斯用自己做实验得出的一条曲线，它说明新学内容的遗忘先快后慢……</p>
</div>
```

**为什么有效**：这一段满足三个条件——出现在正文最前、语义自足（脱离上下文可独立成立）、包含具体事实（年份、人名、结论）。这正是摘录环节最优先抓取的形态。

同样的模式也用在 FAQ 的每个答案上：**第一句就给结论**（「支持。」「没有。」「可以。」），细节放后面。

### 2.2 `llms.txt`

按 [llmstxt.org](https://llmstxt.org/) 规范新建 `/llms.txt`，包含：

- H1 + blockquote 形式的产品一句话摘要（中英双语）
- **核心事实清单**：平台、价格、复习节点、离线边界、词库覆盖、检测方式、隐私处理
- **「它不是什么」章节**：明确排除 AI 聊天工具、课程平台、英英词典、Android/网页版
- 页面索引（带说明的链接列表）
- **引用注意事项章节**（见下）

> `llms.txt` 目前尚未被任何主流 LLM 厂商正式支持，属于「成本极低、可能有收益」的投入。它的**确定收益**是：给人类（包括未来的你）一份产品事实的单一真相来源。

### 2.3 引用护栏（这一条容易被忽略）

`llms.txt` 中显式写明了哪些数字**不该**被当作研究结论引用：

```
- 「第 1、2、4、7、15 天」是墨典单词采用的复习节点，属于间隔重复的常见实践方案，
  并非艾宾浩斯 1885 年论文中的原文内容。
- 官网首页出现的「18 个 vs 5 个」「记忆留存提升 360%」为产品内的示例性对比，
  不是同行评议研究的结论。
```

**为什么要主动设限**：如果 AI 把「360%」当作科学数据传播，一旦被质疑，反噬的是品牌可信度。主动划清边界既保护品牌，也提高内容本身的可信度评级。

### 2.4 术语表 + `DefinedTermSet`

`/glossary.html` 收录 24 个术语，每个包含：中文名、英文名、定义、**「对你的含义」**（可操作解释），并带稳定的 `#id` 锚点与 `DefinedTerm` 结构化数据。

这构成了一组**可被精确引用的定义锚点**。当有人问 AI「什么是合意困难」，一个带定义、带英文对照、带实际应用的独立词条，比埋在长文中间的一句话更容易被摘录。

### 2.5 实体关系

通过 JSON-LD 的 `about` / `mentions` / `sameAs` 把产品与两个已知实体绑定：

- 艾宾浩斯遗忘曲线 → 维基百科条目
- 间隔重复 → 维基百科条目
- 赫尔曼·艾宾浩斯（Person）→ 维基百科条目

这让 AI 在处理「有哪些基于艾宾浩斯遗忘曲线的 App」这类查询时，更容易把墨典单词纳入候选。

### 2.6 结构化格式

AI 摘录偏好结构化内容。已在关键页面加入：

| 结构 | 位置 |
|---|---|
| 复习节点表（次序 / 天数 / 间隔 / 做什么） | 支柱长文 |
| 常见误引对照表（常见说法 / 需要补充的前提） | 支柱长文 |
| 每日词量三档表（时间 / 词量 / 总处理量 / 适合谁） | 博客 #31 |
| 考试倒推表（目标 / 词量 / 30 词 / 40 词 / 建议提前） | 博客 #31 |
| 有序步骤列表 | 支柱长文、博客、下载页、英文页 |

### 2.7 robots.txt 显式放行

GPTBot、OAI-SearchBot、ChatGPT-User、ClaudeBot、Claude-SearchBot、Claude-User、PerplexityBot、Perplexity-User、Google-Extended、Applebot-Extended、CCBot、meta-externalagent 全部 `Allow: /`。

> **这是一个需要产品方明确同意的决策**：放行意味着内容可能被用于模型训练与 AI 回答。对本站而言，被引用的曝光价值远大于内容被使用的顾虑——网站内容本来就是为了被人读到。但如果日后策略改变，收紧点就在这个文件。

## 四、内容层面的 GEO 原则（供长期执行）

### 该做的

1. **每篇文章开头一段自足回答。** 不铺垫、不设问、不「在开始之前我们先来了解一下」。
2. **给出具体数字和出处。** 「Roediger 与 Karpicke 在 2006 年的实验中发现……」比「研究表明……」的引用价值高一个数量级。
3. **主动澄清常见误解。** 纠偏型内容（如「遗忘曲线的数据可信吗」）在 AI 搜索中的引用率明显高于综述型内容，因为它提供了别处没有的信息。
4. **写清楚产品不做什么。** AI 在回答「有没有支持 X 的 App」时，需要判断匹配度。明确的边界说明能减少错误推荐，也减少错配用户。
5. **保持事实的单一来源。** 价格、平台、功能只在 `llms.txt` 和 FAQ 中维护一份，其他地方引用它们——不一致的事实会降低整体可信度。

### 不该做的

1. **不要写「为 AI 优化」的填充段落。** 那种「总结：本文介绍了……」的机械小结既不帮读者也不帮 AI。
2. **不要堆砌问句式小标题。** 三四个真问题好过二十个凑数的。
3. **不要虚构统计数据。** AI 引用后被发现是编的，代价远大于收益。
4. **不要用 JS 渲染核心内容。** 本站是纯静态 HTML，天然满足——但如果日后引入框架，务必保证核心文本在初始 HTML 中。

## 五、效果测量

AI 搜索的曝光**没有官方数据面板**，只能用间接方法：

### 5.1 手动引用测试（建议每月一次）

固定一组查询，在各引擎里跑一遍，记录是否被引用、排在第几：

| 查询（中文） | 查询（英文） |
|---|---|
| 有哪些支持离线的背单词 App | offline vocabulary apps that work without internet |
| 艾宾浩斯遗忘曲线的复习时间是怎么安排的 | what are the optimal spaced repetition intervals |
| 每天背多少个英语单词比较合适 | how many new words should I learn per day |
| 为什么背了单词很快就忘 | why do I forget vocabulary so fast |
| 无广告买断制的背单词软件推荐 | vocabulary app one-time purchase no ads |
| 墨典单词是什么 | what is Modian Words app |

**记录模板**：日期 / 引擎 / 查询 / 是否提及产品 / 是否给出链接 / 引用了哪个页面 / 事实是否准确。

**「事实是否准确」这一列最重要**——如果 AI 说错了产品信息（例如说它有 Android 版），说明站内事实表述不够清晰，需要回头加固 `llms.txt` 与 FAQ。

### 5.2 服务器端信号

GitHub Pages 不提供访问日志。若日后迁移到 Cloudflare Pages，可在日志中筛选 `GPTBot` / `PerplexityBot` / `ClaudeBot` 的 User-Agent 抓取频率，作为 AI 收录的先行指标。

### 5.3 referral 流量

Perplexity 与 ChatGPT 的引用会产生 referral 流量。**但本站当前没有任何分析工具**——这是一个真实的盲区。

> **建议**（见 action-plan P1）：接入一个轻量、无 Cookie、隐私友好的分析工具（如 Plausible 或 Umami 自托管）。注意这会引入一个外部脚本，与当前「零外部依赖」的架构相冲突，需要权衡。**如果选择保持零依赖，就接受 AI referral 无法测量这个事实**，只靠 GSC 与手动测试。这是一个价值观选择，不是技术问题。

## 六、当前的真实局限

诚实记录，避免过度承诺：

1. **新站没有权重。** AI 搜索的检索层高度依赖传统排名信号。在 GSC 里看到稳定曝光之前，AI 引用会很稀少。**GEO 不能绕过 SEO 的爬坡期。**
2. **中文 AI 搜索生态不成熟。** 国内 AI 产品（豆包、Kimi、文心）的检索来源与引用规则不透明，且多依赖国内内容生态。针对它们的优化目前缺乏可靠方法论——**不建议为此做特殊改造**，把基础内容做好即可。
3. **`llms.txt` 尚无厂商正式支持。** 它是低成本押注，不是确定收益。
4. **无法测量 AI 曝光。** 见 5.3。
5. **产品品类的天然限制。** 「背单词 App」这类查询，AI 大概率优先提及墨墨背单词、百词斩这些用户基数大、被广泛讨论的产品。**墨典单词的机会在细分语义位**——「离线」「买断制」「无广告」「无社交」，这些是它能真正独占的位置，也是 `llms.txt` 中着重强调的部分。
